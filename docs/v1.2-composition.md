# v1.2 — Command chaining, output redirection, and piping

Status: implemented in the development tree (Stages 1 and 2). This does not change
the published v1.0.0 release, banner version, or release artifacts.

## User-facing behaviour

- `command && command`: execute the next pipeline only if the last executed
  pipeline returned zero. Skipped pipelines leave the status unchanged.
- `command; command`: execute the next pipeline regardless of status.
- `command | command`: buffer stdout and feed it into the following stage.
  The pipeline status is the final stage's status, not the first failure (no pipefail).
- `command > file`: create or truncate the target before running the command.
- `command >> file`: create or append to the target.
- `exit` stops the shell and prevents later stages or chained commands from running.
- stderr remains separate: diagnostics are neither piped nor redirected.

Operators are recognized outside both single and double quotes. Backslashes remain
literal Windows path characters, not quote escapes. Operators need no surrounding
spaces: `echo hello>out.txt` works. Quoted targets such as `>"my output.txt"` work.
Relative output paths are resolved at execution time, so `cd folder; pwd >cwd.txt`
writes inside the new directory. Redirection targets support the existing `~`
expansion. Parsing an invalid line fails before any command on that line executes.
A trailing semicolon is accepted; a trailing `&&` or `|`, an empty command, an
unclosed quote, or a missing/empty output target is a parse error (status 2).
Multiple output redirections on one command are rejected rather than silently
choosing a target.

Redirection overrides a stage's pipe output: `echo text >out.txt | grep text`
writes to `out.txt` and supplies an empty input to `grep`. File-open/write errors
set a failure status. Redirection is intentionally destructive with `>`; unlike
`cp` and `mv`, it does not protect an existing target from overwrite.

### Examples

```text
mkdir -p reports && ls -la > reports/listing.txt
echo first > notes.txt; echo second >> notes.txt
ls -la | grep .cpp | grep -i parser
cat notes.txt | findstr.exe second | grep second
ls -la | grep .cpp > "cpp files.txt"
echo "literal && ; | > >>"
```

### grep input and colours

`grep [-i] [-n] <pattern> <file>` retains ordinary file-based searching. Inside a
pipe, `grep [-i] [-n] <pattern>` reads the preceding stage's complete output via
`std::istringstream`. If a file operand is also supplied, pipe input takes priority.
Empty piped input is still an input source: it never falls back to a file or console.

Matching is literal, with ASCII-only case folding for `-i`. `-n` counts input lines.
ANSI CSI sequences (including colours) and OSC sequences are removed from each line
before matching and highlighting. Thus colour parameters cannot produce false
matches, visible text split by colour codes still matches, and repeated `grep`
stages work. Original upstream colours are not preserved; matching text receives
ArcNova's normal highlight, including when written to an output file.
Exit codes remain 0 for matches, 1 for no matches, and 2 for usage/I/O errors.

## Implementation map

| File | Change |
| :--- | :--- |
| `include/core/parser.hpp` | Adds `ChainOp`, `CommandPipeline`, `redirectOutFile`, `appendMode`, `parseLine()`, and optional `pipedInput`. |
| `src/core/parser.cpp` | Splits unquoted chaining/pipe operators; tokenizes redirection independently of whitespace; validates syntax and removes output operators/targets from arguments and external raw input while retaining original command quoting. |
| `include/core/shell.hpp` | Adds an optional output-capture argument to `executeCommand()`. |
| `src/core/shell.cpp` | Evaluates chaining; captures intermediate stdout with `std::stringstream`; passes input to the next stage; redirects built-in output using `std::ofstream` and an RAII stream-buffer guard. |
| `include/core/executor.hpp` | Extends external execution with output-target, append, pipe-input, and capture parameters; defaults retain existing callers. |
| `src/core/executor.cpp` | Sets child stdin/stdout handles for piped/redirected execution; trims surrounding command-line whitespace before `CreateProcessW`; retains process waiting, exit codes, and cmd fallback. |
| `src/commands/sys_commands.cpp` | Makes `grep` pipe-aware and removes ANSI codes before matching/highlighting. |

`CommandPipeline::nextChainOp` connects that pipeline to the following pipeline.
`pipedInput` is `std::optional<std::string>`: `nullopt` means no upstream pipe;
an engaged empty string means upstream emitted no data.

Built-in output redirection restores the previous `std::cout` buffer and state on
scope exit, including command-handler exceptions. File writes are flushed and
checked. An intermediate redirect nests inside the pipeline capture guard.

External processes do not write through C++ `std::cout`, so they require Win32
handles. Output files use `CREATE_ALWAYS` for overwrite or `OPEN_ALWAYS` with
`FILE_APPEND_DATA` for append. Buffered external stdin/stdout use inheritable,
temporary, delete-on-close spool files. Input is written and rewound before spawn;
captured output is rewound and copied to `std::cout` after the child finishes.
This avoids the wait-before-drain deadlock of synchronous anonymous pipes when
output exceeds pipe capacity. Handles are closed by RAII; stderr still inherits
the shell's original error handle. No `system()` or third-party library is used.

## Limits and compatibility

- Stages execute sequentially with whole-output buffering, not concurrently.
  Infinite streams and interactive pipeline stages are unsuitable. Large pipelines
  consume memory, and external stages additionally require writable temporary storage.
- Built-in `grep` consumes pipe input; other built-ins keep their existing behaviour.
  In particular, `cat` still needs file operands. External programs receive native
  stdin and can consume it if they support redirected input.
- No native `<`, `2>`, `2>&1`, `||`, background jobs, grouping, or pipefail support.
  Descriptor syntax such as `2>` must not be used: the parser interprets `>` as
  stdout redirection, not a descriptor operator. Some remaining cmd syntax may be
  handled by external-command fallback, but is not an ArcNova language contract.
- Built-ins run in the shell process: directory changes inside a pipeline persist.
- Output redirection captures only stdout. Existing colour sequences may be stored
  in files; automatic colour suppression for non-console output is not implemented.
- Native parsing precedes external execution. Quote metacharacters intended for a
  nested command interpreter; unquoted operators belong to ArcNova.
- Existing raw-input editing, history, filesystem safeguards, and release version
  labels are unchanged.

## Verification

Compile all sources with C++17 and warnings treated as errors:

```powershell
g++ -std=c++17 -O2 -Wall -Wextra -Werror -Iinclude -fsyntax-only src/main.cpp src/core/*.cpp src/commands/*.cpp
```

The implementation was also exercised with temporary assertion-based C++ harnesses
outside the repository. They covered:

- Quoted operators, adjacent redirection, quoted targets, append flags, raw-input
  removal, blank lines, trailing semicolons, and malformed syntax.
- Successful/failed `&&`, unconditional `;`, overwrite/append, and external output
  redirection, while retaining the output file after a skipped command.
- Built-in pipelines, three-stage pipelines, no matches, empty pipe input, and
  `&&` after a failing final stage.
- External-to-built-in, built-in-to-external, and external-to-external stages using
  `cmd.exe` and `findstr.exe`, plus final file redirection.
- ANSI-split visible text matching, absence of matches against colour parameters,
  and existing file-based `grep`.
- A 20,000-line pipeline through `findstr.exe` and numbered `grep`, exceeding a
  typical anonymous pipe buffer without deadlocking.

These temporary harnesses are not a checked-in automated regression suite. For
manual verification, build the shell and run the examples above in a disposable
directory. Confirm file contents, prompt success/failure colours, absence of
intermediate console output, and continued console output after redirection.
